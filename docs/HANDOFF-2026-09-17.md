## 4. Gotchas found this session — save yourself the rediscovery

1. **`git worktree add` does not initialize submodules.** `vendor/kubediagrams` and
   `vendor/kroki-mcp` are git submodules; a fresh worktree leaves them as empty
   directories. Run `git submodule update --init --recursive` in any new worktree
   before `just pod-build`. This silently broke a container build — the `COPY
   vendor/kubediagrams/bin` step failed, but the failure was masked (see #2) so the
   pod ran a **stale image** for a while without anyone noticing.
2. **`command | tail -N` hides `command`'s real exit code.** A failed `just pod-build`
   piped through `tail -80` reported "completed (exit code 0)" — it was `tail`'s exit
   code, not the build's. Always `set -o pipefail` before piping a build command, or
   check the exit code separately.
3. **This host is memory-constrained.** The local LLM container
   (`b00t-ch0nky-llamacpp`, Qwen, ~9GB RSS) plus everything else running left very
   little headroom. Large `podman save | k0s ctr images import` pipelines (the
   2.86GB `kroki-compat` image especially) got killed by a background-task memory
   guard repeatedly — **running the same command in the foreground (not
   `run_in_background`) succeeded every time.** If you hit this again: try foreground
   first before assuming you need to free memory by stopping other containers.
4. **This session's own `mcp__kr0ki-mcp__*` tools disconnect when the pod is
   recreated** (the underlying `kubectl exec` session dies) and do not
   auto-reconnect within the session. If you need to validate the MCP path after a
   pod restart, either start a fresh session or manually exercise the same command
   `.mcp.json` uses: `kubectl --context Default -n kr0ki exec -i pod/kr0ki-local -c
   kr0ki-mcp -- python3 /opt/kr0ki-mcp/bridge.py` with a JSON-RPC request piped in.
