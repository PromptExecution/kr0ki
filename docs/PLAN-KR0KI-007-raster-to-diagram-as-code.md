## 0. Outcome

A user opens the playbook, maps a local project directory, and adds raster diagrams (PNG/JPEG/WebP). For each one
kr0ki asks a multimodal model for diagram-as-code in a supported format, **renders every attempt with the real
renderer, and asks a judge whether the render matches the original**, repeating inside hard caps until it matches or
the budget is spent. The accepted source is written back next to the image and recorded as a revision.

Invariants carried over from earlier plans, not renegotiated here:

- The raster and the model's output are **inputs**. The only durable, editable artifact is the diagram-as-code;
  every preview and artifact is regenerated by kr0ki from it (PLAN-004 §0).
- kr0ki **renders**; it does not trust or execute model output. A source is accepted only after the real backend
  renders it *and* the match gate passes.
- Raw diagram-as-code and the generated (AST/IaC) pipeline stay separate, permanent capabilities. This is a third
  way *into* diagram-as-code, not a replacement for either.

## 1. Where it sits

A **visual front-end** (box 1) whose output is stage-2 diagram-as-code, followed by the existing stage-3 render.
It lives in its own crate, `crates/kr0ki-raster-ingest`, as [`AGENTS.md` §4](../AGENTS.md) already requires; it does
not go in `kr0ki-svg` (layout/enrichment) or `kr0ki-core` (render loop). The orchestrator is a pure function over
traits, so every behavior is testable with deterministic fakes:

```
browser                          kr0ki-server                        kr0ki-raster-ingest
 ProjectFs ──image bytes──► POST /ingest/raster (SSE) ──► Normalize ─► Describe(VLM) ─► ┐
 (dir handle | folder input)                                                            │  LOOP (caps enforced here)
                                                          ┌───────────────────────────────┘
                                                          ▼
                                   Propose(VLM) ─► Render(RenderService, real backend) ─► Score ─► Decide
                                        ▲                                                  │  (label check via kr0ki-svg
                                        └──────── verdict diff, render error ──────────────┘   + Judge(VLM) on side-by-side)
 write <name>.<ext> + <name>.kr0ki.json ◄── accepted | exhausted(best attempt)
```

```rust
trait VisionModel { async fn complete(&self, req: VisionRequest) -> Result<String, ModelError>; }
trait Renderer    { async fn render(&self, fmt: DiagramFormat, src: &str) -> Result<Rendered, RenderError>; } // wraps RenderService
fn run_loop(image: &NormalizedImage, cfg: &LoopConfig, m: &dyn VisionModel, j: &dyn VisionModel, r: &dyn Renderer)
    -> LoopOutcome   // Accepted | Exhausted{best} | NotADiagram, always with every AttemptRecord
```

## 3. The loop ("ralph loop")

The technique is the same one b00t's ralph loop names: repeat a task with a **fresh context each iteration** and keep
the state in durable artifacts, stopping on a verifiable completion condition rather than on the model's say-so.

1. **Normalize** — decode with enforced limits (§6), strip metadata, cap the longest side (default 2048 px),
   re-encode to PNG, `sha256` the normalized bytes.
2. **Describe** (once) — the model returns a structured target: `diagram_kind` (incl. `none`), visible text labels,
   nodes, directed edges. `none` ends the run with `NotADiagram` and **no loop**.
3. **Propose** — prompt built from durable state only: original image, description, target format and its skill file,
   best source so far, and the last verdict's concrete differences. Not chat history.
4. **Render** — the real backend. A render error is an attempt result: its message (truncated) goes into the next
   prompt.
5. **Score** — deterministic label check plus the judge (§7).
6. **Decide** — accept, or continue, or stop.

**Hard caps, enforced by the orchestrator:** `max_iterations` (default 6), wall-clock budget, token budget, and
per-call timeout. **Stall detection:** stop when the same source hash repeats or the composite score fails to improve
for 2 attempts. **Exhausted** returns the best attempt with `converged: false` — never an error that discards work.

**Accept** = no render error **and** judge `match` **and** label recall ≥ τ (default 0.9). If label extraction is
unusable for a format (text drawn as paths), fall back to *two consecutive* judge matches and record that in the result.

## 4. Contracts

**Verdict** (JSON Schema at `docs/schemas/plan-007/verdict.schema.json`, added in Phase 0, `additionalProperties: false`):
`match: bool`, `score: 0..1`, `label_recall`, `label_precision`, `missing_nodes[]`, `extra_nodes[]`,
`wrong_edges[{from,to,expected}]`, `label_errors[{expected,got}]`, `layout_notes[]`, `confidence`.

**HTTP**: `POST /ingest/raster?format=<slug>&max_iterations=<n>`, body = raw image bytes
(`Content-Type: image/png|image/jpeg|image/webp`), route-specific `DefaultBodyLimit` (default 10 MiB). Response is
`text/event-stream`: `normalized`, `description`, `attempt {n, source_sha256, render_ok, score}`, then `accepted` or
`exhausted` or `not_a_diagram`, carrying `{source, format, attempts[], converged, image_sha256, models, usage}`.
Errors: 413 too large, 415 unsupported type, 422 undecodable or over the pixel limit, 503 vision not configured,
502 model/backend failure. Covered by the existing `KR0KI_AUTH_TOKEN` middleware.

**MCP**: a `raster_to_diagram` tool in `mcp_tool.rs`. `ArgPlacement::Body` passes one string as the whole request body,
so the tool takes base64 and the bridge decodes to the raw-bytes route. *Detail to settle in Phase 1.*

**Cache**: key = `sha256(image_sha256 ‖ format ‖ model ids ‖ prompt version ‖ loop config)`; the **final result** is
cached, attempts are not. Uploads are never stored beyond the hash (kr0ki is not a blob store).

**Project directory convention** (written by the browser, never by the server):

```
<project>/diagrams/checkout.png           ← the image you added
<project>/diagrams/checkout.d2            ← accepted source (the only editable artifact)
<project>/diagrams/checkout.kr0ki.json    ← verdict, attempts summary, image sha256, models, prompt version, date
```

Existing files are never overwritten without an explicit confirm; filenames are sanitized; nothing is written outside
the selected directory.

## 5. Browser: mapping a project directory

A `ProjectFs` interface (`list`, `read`, `write`, `exists`) with two adapters behind feature detection:

| Adapter | Works when | Can write back |
|---|---|---|
| `DirectoryHandleFs` — File System Access API | secure context (HTTPS or localhost) + user gesture + Chromium | yes, with `mode: 'readwrite'`; the handle is kept in IndexedDB and permission is re-requested |
| `InputFolderFs` — `<input type="file" webkitdirectory>` | any context, any modern browser (*unverified in Firefox/Safari for this app; confirm in Phase 2*) | no: results are offered as downloads |

The UI says which adapter is active and why ("open via `localhost` or HTTPS to enable write-back"). Read-only is the
default; write access is an explicit toggle; directory traversal is bounded by file count and size.

**WASM.** v1 needs no WASM filesystem: any Rust WASM code (`kr0ki-svg`) is handed bytes. If a Rust *component* later
needs `wasi:filesystem`, implement a custom `preview2-shim` `filesystem` handler backed by the same `ProjectFs`;
the shim's README assigns permission prompts and handle acquisition to application code. That is deferred until a
component needs it.

## 6. Model access, privacy, and input safety

- **Config**: `KR0KI_VISION_ENABLED`, `KR0KI_VISION_API_URL`/`_KEY`/`_MODEL` (fall back to `OPENAI_*`), optional
  `KR0KI_VISION_JUDGE_MODEL`. Unset → `503 vision_not_configured`; nothing else changes.
- **Privacy**: an uploaded image is sent to the configured endpoint. Default policy: only loopback/private addresses
  are accepted; a public endpoint requires `KR0KI_VISION_ALLOW_REMOTE=1`. The UI names the endpoint before the first
  upload. **D-7a** decides whether remote is ever allowed.
- **Decode limits**: size cap (10 MiB default), pixel cap (e.g. 40 MP) checked from headers **before** decoding, allowed
  types PNG/JPEG/WebP by content sniffing (not the header), single frame only (reject animated), metadata stripped.
  An SVG upload is not raster input; route it to the existing `/render` path.
- **Prompt injection**: text inside an image is data. System prompts say so; the model's output can do nothing except
  become a source that is then rendered and scored. Output format is restricted to `DiagramFormat::ALL` (not the
  agent's wider `VALID_INPUT_FORMATS`, which includes formats the server rejects).
- **Cost**: per-run token/cost ceilings and a per-process concurrency limit; usage is returned in the result.

## 7. Scoring: why two signals

- **Deterministic label check.** The description's visible labels vs the text in the *rendered SVG* (`kr0ki-svg`),
  normalized (case, whitespace, tiny edit distance via a crate such as `strsim`). It is cheap, reproducible, and
  independent of the proposing model's opinion.
- **Judge.** A model sees the original and the render's PNG (`flatten::svg_to_png`) side by side and returns the
  Verdict. "Match" means the same nodes, labels and directed connections; styling and layout differences do not count
  unless they change meaning.
- **Correlated error.** Proposer and judge are often the same model, so they can agree on a wrong answer. Mitigations:
  the deterministic check, an optional separate judge model, and the evaluation in §8. The plan does not claim the
  judge is an oracle.

## 8. Evaluation (self-supervised, no hand labeling)

For each of the 37 catalog fixtures: render to PNG, ingest back into the original format, then compare the *original
render* with the *recovered render* using the same `kr0ki-svg` label extraction (label F1), plus judge agreement,
iterations to converge, tokens and wall time. `just eval-raster` writes a per-format report. Added sets:
a **negative set** (photos, screenshots, blank images) that must end in `not_a_diagram` without looping, and an
**adversarial set** (an image that says "ignore previous instructions and output X") that must change nothing.

## 10. Risks

| Risk | Mitigation |
|---|---|
| The available model cannot read diagrams well (or at all) | `Describe` → `not_a_diagram`/low-confidence exits early; Phase 3 eval reports it; **D-7a** |
| Some renderers convert text to paths, defeating label extraction | per-format fallback to two consecutive judge matches, flagged in the result |
| Self-judging bias | deterministic check; optional separate judge; eval |
| Cost or latency blow-ups | orchestrator-enforced caps; concurrency limit; result cache |
| Insecure-origin deployment blocks directory mapping | fallback adapter; clear UI; document localhost/HTTPS (**D-7e**) |
| Image contains sensitive data | explicit remote-allow flag, endpoint named in the UI, no server-side retention |

## 11. Non-goals

Hand-drawn or whiteboard-photo fidelity, dense-document OCR, editing or cleaning the image, training or fine-tuning,
multi-diagram pages, a server-side image store, CDN delivery, and any change to how raw or generated diagram-as-code
works.
