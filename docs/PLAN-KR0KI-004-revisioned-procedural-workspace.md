# PLAN-KR0KI-004 — revisioned procedural workspace

**Parent:** [`PRD-KR0KI-001-foundational.md`](PRD-KR0KI-001-foundational.md), renderer
Box 5. **Related:** [`PLAN-KR0KI-002.md`](PLAN-KR0KI-002.md) (the source-to-render
pipeline), [`docs/superpowers/specs/2026-09-17-storyb00k-agent-dashboard-design.md`](superpowers/specs/2026-09-17-storyb00k-agent-dashboard-design.md)
(the shipped StoryB00k prototype). **Owner:** PromptExecution. **Created:** 2026-09-18.

**Status:** proposed. This is a contract-first plan; it authorizes no orchestration
framework or assistant-ui dependency change until Phase 0 accepts the contracts below.

---

## 0. Outcome

Build StoryB00k into a **revisioned procedural workspace**: an authenticated user is
granted one bounded development project workspace, can discuss a diagram with an
assistant, and can inspect each proposed change as an immutable, reproducibly rendered
attempt. The user may accept, reject, restore, or fork an attempt. Named branches,
semantic merge, and project-Git materialization follow only after linear revisions are
correct.

The diagram artifact (SVG/PNG/HTML) is never editable state. The only editable state is
the canonical diagram program or typed procedural model captured in a revision. Every
preview, comparison, and accepted artifact is regenerated by kr0ki from that revision.
That invariant is the definition of “always procedurally generated.”

The browser is Vue, chat/tool presentation is **assistant-ui only**, and agent transport
is AG-UI. CopilotKit is expressly excluded. No agent orchestration framework
(LangGraph, LangChain, Vercel AI SDK workflow layer, or equivalent) is introduced while
the workspace/revision contract remains unsettled.

## 1. Observations and decision

The current `playbook/` is a useful proof of transport, not yet a workspace product:

- It uses `@ag-ui/client` and `@synoped/ag-ui-vue` to show a transcript and panels.
- `containers/kr0ki-storyb00k-agent/server.py` is a small OpenAI-compatible sidecar
  that emits AG-UI events and calls a static `/mcp/tools` manifest.
- Its `DraftGraph` is process-memory state, shared only by thread ID. It has no user,
  project grant, durable revision, diff, branch, approval history, or safe browser
  mutation model.
- The current dynamic-looking tool manifest is cached globally. It cannot safely
  describe a particular user's workspace or revision.

assistant-ui now has a Vue package and Vue tool UI primitives, so this plan uses the
native Vue path rather than a React island. Its documented custom runtime boundary also
allows an application transport instead of requiring a backend framework. AG-UI remains
the streaming event protocol, with a small adapter if the installed Vue package does not
yet expose a direct AG-UI runtime adapter. [assistant-ui Vue](https://www.assistant-ui.com/docs/vue),
[custom runtimes](https://www.assistant-ui.com/docs/runtimes/custom/overview), and
[AG-UI runtime](https://www.assistant-ui.com/docs/runtimes/ag-ui/overview) support this
division.

### 1.1 Product invariants (the contract to implement first)

1. **Immutable attempts.** A revision is append-only. Editing creates a new revision;
   it never changes a historical revision, its source, provenance, rendered artifact,
   or tool record.
2. **Procedural output.** A revision has canonical input plus a pinned compiler/renderer
   version and input hash. Artifacts are derived output addressed by those values. SVG
   DOM edits, raster edits, and hand-patched renderer output are rejected.
3. **Explicit lineage.** Every revision records one or more parent revision IDs, author
   (human or agent identity), intent, ordered operation list, timestamps, and status.
   The result is a DAG, even when the first release exposes only a linear history.
4. **Revision-scoped writes.** Every mutation carries `workspace_id` and
   `expected_revision_id`. A stale write is rejected with a conflict; it must not
   silently overwrite another attempt.
5. **User-controlled promotion.** Agent mutations first create a `proposed` revision.
   Only a user action may make that revision the active branch head or materialize it
   into a developer project.
6. **Bounded project authority.** A session grants an identity access to one workspace
   and its declared project root/capabilities. The model receives no ambient filesystem,
   shell, network, or browser-script authority.
7. **Declarative UI mutation.** The agent requests typed workspace/UI operations; Vue
   renders the resulting state. It may not send JavaScript, CSS, arbitrary DOM selectors,
   `eval`, or an unrestricted browser automation command.
8. **Replayability.** Given a revision's canonical input, operation records, and pinned
   compiler/renderer identifiers, the service can regenerate the preview and verify its
   artifact hash.

## 2. Domain model and state contract

The service owns this model in `kr0ki-server`; it is session/revision metadata, not a
new UFO semantic-model layer and therefore does not belong in `kr0ki-core`.

```text
UserSession ──grants──> Workspace ──has──> Branch ──head──> Revision
                              │                         │
                              ├── project grant          ├── parent revision ID(s)
                              ├── conversation           ├── canonical input
                              └── capability policy      ├── operation/provenance log
                                                        ├── render recipe/artifact hash
                                                        └── proposed | accepted | rejected | merged
```

Minimum persistent records:

| Record | Required fields | Meaning |
|---|---|---|
| `Workspace` | `id`, `owner_id`, `project_id`, `active_branch_id`, capability policy, timestamps | Bounded collaboration unit. Its project grant is immutable except through an audited admin/user action. |
| `ProjectGrant` | `project_id`, allowed root/worktree reference, allowed render formats, read/write/materialize flags | Names the development project the session may see. It is not a shell grant. |
| `Branch` | `id`, `workspace_id`, `name`, `head_revision_id`, timestamps | A mutable pointer; revisions themselves are immutable. MVP exposes `main` only. |
| `Revision` | `id`, `workspace_id`, `parent_ids`, `branch_id`, `status`, `author`, `intent`, `canonical_input`, `input_kind`, `input_hash`, `renderer_recipe`, `artifact_hash`, timestamps | One attempted procedural state. `canonical_input` is either validated diagram-as-code or a typed model snapshot—not an artifact. |
| `RevisionOperation` | `revision_id`, sequence, tool name/version, validated arguments, result digest, actor | Audit/replay trace. Store secrets redacted and large result bodies by content reference. |
| `ConversationEvent` | `workspace_id`, `conversation_id`, sequence, AG-UI event, actor, revision reference | Durable conversation/activity trail; not a replacement for revision provenance. |
| `Approval` | `revision_id`, approver, decision, reason, timestamp | The required human promotion decision. |

### 2.1 Canonical input lanes

Start with a validated `DiagramSource` lane (`format`, source text, render options),
because kr0ki already renders it. Add a `ProceduralModel` lane only when its compiler
contract is defined by the upstream typed-model work. Both lanes satisfy the same rule:

```text
revision canonical input + pinned recipe --> kr0ki render --> immutable artifact
```

Raw diagram source is a program, not a visual artifact. A typed JSON Patch is accepted
only against a schema/version for that lane. The server validates, canonicalizes, hashes,
and renders before storing a `proposed` revision. The client never supplies an artifact
hash as proof of correctness.

### 2.2 Wire state

On join/reconnect the server emits an AG-UI `STATE_SNAPSHOT`; subsequent changes are
AG-UI `STATE_DELTA` operations. The snapshot is a projection, not the persistence model:

```json
{
  "workspace": { "id": "ws_…", "project": { "id": "project_…", "name": "…" }, "capabilities": ["diagram.read", "diagram.propose"] },
  "conversation": { "id": "conv_…", "messages": [], "activity": [] },
  "branches": [{ "id": "branch_main", "name": "main", "headRevisionId": "rev_…" }],
  "activeRevision": { "id": "rev_…", "status": "accepted", "inputKind": "diagram_source", "source": "…", "artifact": { "url": "…", "hash": "…" } },
  "revisionGraph": { "nodes": [], "edges": [] },
  "selection": { "entityId": null, "revisionId": "rev_…" },
  "pendingApproval": null
}
```

The project root, credentials, raw tool results, and hidden policy fields are never
placed in browser state. Event sequences must conform to AG-UI's snapshot/delta model;
the server should retain enough event history to recover from a reconnect.

## 3. Interaction and procedural change flow

```mermaid
sequenceDiagram
    participant U as User
    participant V as Vue + assistant-ui
    participant A as StoryB00k agent sidecar
    participant W as Workspace service
    participant K as kr0ki renderer

    U->>V: “Group services by bounded context”
    V->>A: AG-UI message + active workspace/revision
    A->>W: workspace.propose_patch(expected_revision_id, typed patch)
    W->>W: validate grant, schema, lineage; create proposed revision
    W->>K: render canonical input with pinned recipe
    K-->>W: content-addressed artifact
    W-->>A: revision + artifact + structured diff
    A-->>V: AG-UI tool activity, STATE_DELTA, explanatory message
    V-->>U: preview, diff, revision card, Approve / Reject / Fork
    U->>W: approve(revision_id) or reject(revision_id)
    W-->>V: new branch head or immutable rejection record
```

The agent can explain and propose; the workspace service is the sole writer of durable
state. Rendering happens server-side through the existing `RenderService`, preserving
its content-addressed cache and making “preview” identical to the artifact that will be
accepted.

## 4. Dynamic MCP and browser authority

Keep kr0ki's existing static render tool manifest intact. Add a **workspace-scoped tool
catalog** in the StoryB00k sidecar/service boundary. It is dynamic because its schemas
and allowed choices are derived from the active workspace revision and capability policy,
not because it can execute arbitrary commands.

Initial catalog:

| Tool | Required arguments | Result |
|---|---|---|
| `workspace.read_state` | `workspace_id`, `revision_id` | Redacted canonical state and revision graph projection. |
| `workspace.propose_patch` | `workspace_id`, `expected_revision_id`, lane-specific typed patch, intent | New validated `proposed` revision; never changes branch head. |
| `workspace.render_attempt` | `workspace_id`, `revision_id` | Re-render/verify the stored recipe and return artifact metadata. |
| `workspace.compare_revisions` | `workspace_id`, left/right revision IDs | Structural/source diff plus artifact links. |
| `workspace.accept_attempt` | `workspace_id`, `revision_id`, expected head | Human-only promotion to current branch head. |
| `workspace.reject_attempt` | `workspace_id`, `revision_id`, reason | Immutable rejection/audit event. |
| `workspace.checkout_revision` | `workspace_id`, `revision_id` | UI selection; does not rewrite history. |
| `ui.focus_entity` / `ui.show_diff` | entity or revision IDs only | Declarative client-state command, validated against the current snapshot. |

Every tool definition is generated with a catalog version and includes workspace and
revision preconditions. Cache it by `(workspace_id, active_revision_id,
capability_policy_version, catalog_version)`, replacing the sidecar's process-global
manifest cache. Authorization is checked again at invocation; a tool schema is never an
authorization decision.

Formal MCP exposure is a later adapter, not an MVP dependency. If external MCP hosts
need rich interactive output, use MCP Apps' sandboxed `ui://` resource model and
bidirectional message channel rather than browser DOM access. [MCP Apps overview](https://apps.extensions.modelcontextprotocol.io/api/documents/overview.html).
For the first-party Vue app, AG-UI state events and typed UI commands are sufficient.

## 5. Experience specification

Replace the prototype's transcript-plus-panels layout with a three-pane workspace:

```text
┌ Conversations / Workspaces ┬ Procedural canvas + compare mode ┬ Inspector / Revision DAG ┐
│ project grant, threads     │ rendered artifact, source/model   │ selected node, diff,      │
│ search, new conversation   │ graph overlays, activity trail    │ lineage, approval actions │
└────────────────────────────┴───────────────────────────────────┴──────────────────────────┘
                                      └──── assistant-ui composer / tool cards ────┘
```

- **Conversation rail:** workspace/project identity, thread list, search, and clear
  capability cues. A conversation is always attached to one workspace.
- **Canvas:** generated artifact with pan/zoom, selection, rendering state, and a
  before/after compare mode. The canvas has a visible “derived from revision” badge
  carrying revision and artifact hashes.
- **Revision inspector:** a navigable DAG, source/semantic diff, prompt/agent/tool
  provenance, renderer recipe, and Accept / Reject / Restore / Fork controls.
- **assistant-ui composer and activity:** streaming text, structured tool-call cards,
  explicit pending approval card, retries/errors, and suggestions grounded in the
  selected revision. Use assistant-ui Vue tool UI APIs; do not recreate a separate chat
  component system. [assistant-ui tool UI](https://www.assistant-ui.com/docs/vue/tool-ui).
- **Accessibility:** keyboard focus follows `ui.focus_entity`, approval controls are
  keyboard reachable, and the canvas has a text/structured alternative for revision and
  entity information.

“Mutate the DOM” therefore means “make a typed state request whose visible effect Vue
renders.” This gives the agent useful interface control without granting script injection
or allowing an untracked visual state to diverge from the procedural model.

## 6. Delivery plan with specific actions

### Phase 0 — freeze and prove the boundary (no product migration yet)

1. Write an ADR beside this plan that adopts assistant-ui Vue as the sole chat/tool UI
   library, AG-UI as the agent event protocol, and explicitly rejects CopilotKit.
2. Pin and verify the compatible `@assistant-ui/vue` release. Build a throwaway Vue
   adapter spike that consumes the sidecar's `RUN_*`, message, tool, `STATE_SNAPSHOT`,
   and `STATE_DELTA` events. Prefer an official Vue AG-UI adapter if available; otherwise
   implement a small local assistant-ui custom runtime/transport adapter. Do not add
   React, a second state manager, or an orchestration SDK.
3. Publish JSON Schema (and Rust types) for `Workspace`, `Branch`, `Revision`,
   `RevisionOperation`, approval commands, and the redacted browser snapshot. Decide
   the initial canonical lane as D2 diagram source and list the first accepted patch
   operations.
4. Define an authenticated session/grant interface with a production identity-provider
   decision. For local development only, a signed development session may stand in; a
   bare thread ID is not a session.
5. Exit gate: record a fixture trace from connect through proposed revision/approval/
   reconnect, and get agreement that every state transition has an owner and precondition.

### Phase 1 — durable linear revision service

1. Add `crates/kr0ki-server/src/workspace/` with `types.rs`, `store.rs`, `service.rs`,
   `routes.rs`, and `policy.rs`. Keep `kr0ki-core` stateless and render-focused.
2. Define a `WorkspaceStore` trait with deterministic in-memory implementation for tests
   and a durable SQLite implementation for local deployment. Make DB migrations explicit
   and store canonical JSON/text plus content hashes; use transactions for branch-head
   compare-and-set.
3. Implement routes for create/join workspace, read snapshot, create proposal, compare,
   accept, reject, and checkout. Require session grant plus `expected_revision_id` on
   all writes; return a typed conflict response for stale heads.
4. Call `RenderService` while creating a proposal. Persist the recipe and derived
   artifact metadata only after successful validation/render; retain a failed attempt as
   an auditable failure without promoting it.
5. Replace the in-memory `DraftGraph` as the authority. The Python sidecar becomes an
   agent transport/client of workspace APIs, never the canonical workspace store.
6. Exit gate: restart the service, restore a workspace, render an old revision by hash,
   approve a new revision, and prove that the former revision bytes remain unchanged.

### Phase 2 — assistant-ui Vue workspace shell

1. In `playbook/package.json`, remove the Synoped chat binding after the Phase-0 adapter
   passes; add only the verified assistant-ui Vue packages. Do not add CopilotKit.
2. Split `StoryB00k.vue` into a workspace shell, assistant conversation panel, procedural
   canvas, revision graph, diff viewer, and inspector. Keep Histoire stories for each
   component and fixture event sequence.
3. Implement an external-store/custom-runtime bridge from the AG-UI stream to the
   workspace snapshot. The bridge applies server-authorized state deltas; it does not
   make client-side revision writes.
4. Render structured activity cards for proposal, render, approval, rejection, conflict,
   and retry. Add the three-pane layout, revision badge, compare mode, and keyboard
   navigation defined in §5.
5. Exit gate: a browser fixture can send a prompt, receive a proposed rendered revision,
   show a diff, approve it, reload, and see the same selected branch head.

### Phase 3 — safe agent mutations and dynamic catalog

1. Move workspace tool implementations behind the service policy layer and expose their
   JSON schemas to the sidecar. Remove global manifest caching; construct catalog entries
   per session/revision/capability version.
2. Make `workspace.propose_patch` the only agent write primitive in the MVP. Enforce
   schema validation, source-size limits, renderer-format allowlist, provenance
   recording, idempotency key, and expected-revision compare-and-set.
3. Emit an ordered AG-UI trace: run start, tool intent, proposal-created activity,
   state delta containing derived artifact/diff, approval request, and terminal result.
   Preserve redacted event records for reconnect/audit.
4. Add typed `ui.*` commands with client validation and no raw browser execution. Test
   that arbitrary selector, JavaScript, URL, filesystem, or shell arguments are rejected.
5. Exit gate: two sessions cannot read or alter each other's workspace; a stale proposal
   cannot overwrite a newer head; every rendered preview traces to one stored revision.

### Phase 4 — branches, merge, and project materialization

1. Expose `workspace.create_branch` and named branch heads after the linear store is
   proven. Forking an old revision creates a new pointer; it never rewrites `main`.
2. Specify a three-way merge contract per input lane: common ancestor, deterministic
   patch composition, structured conflicts, user resolution, then a new merge revision
   with two parents. Do not pretend text merge is semantic merge for typed models.
3. Add a user-approved project materialization adapter only for an explicitly granted,
   isolated worktree. It writes a reviewable source change on a dedicated branch; no
   direct default-branch write, `git commit`, pull request, or merge is automatic.
4. Exit gate: fork, make independent proposals, demonstrate a conflict, resolve it into
   a two-parent revision, and materialize only after a separate user approval.

### Phase 5 — external MCP applications (optional)

1. Offer the workspace catalog as a formal MCP server only when an external host needs
   it, including `tools/list_changed`/catalog invalidation and session authorization.
2. For rich host-provided UI, package revision cards or viewers as sandboxed MCP Apps
   resources. Keep first-party Vue state as the source of interaction semantics.
3. Exit gate: an external host can inspect/propose under the same grant and revision
   policy as the first-party browser, with no broadened browser or filesystem authority.

## 7. Test matrix and acceptance criteria

| Layer | Required proof |
|---|---|
| Domain unit tests | Revision IDs/hash determinism, immutable rows, parent validation, status transition table, redaction, stale-head conflict, and rollback/checkout do not mutate history. |
| Renderer integration | Proposal rendering uses its stored recipe; an artifact regenerated from a revision has the recorded digest; renderer failure cannot advance a branch. |
| AG-UI conformance | Fixture streams cover initial snapshot, delta ordering, disconnect/reconnect, tool error, approval request, and interrupted run. |
| Vue component/E2E | Chat → proposal → compare → accept → reload; reject; checkout older revision; keyboard approval; branch display is not mistaken for merge. |
| Security | Session/workspace isolation, capability denial, catalog cache isolation, schema rejection, no direct DOM/eval action, no source/artifact substitution, and no agent project write without approval. |
| Operational | SQLite migration/backup/recovery test, structured audit logs with secret redaction, bounded retention policy for conversation events/artifacts. |

The MVP is accepted only when a user can recover any accepted or rejected attempt by
revision ID, rerender it deterministically, understand why it was proposed, and choose
the active head without an agent silently changing it.

## 8. Explicit non-goals and deferred decisions

- No CopilotKit dependency, adapter, or migration path.
- No generic orchestration framework before the state/revision contracts and trace
  fixtures are accepted. A simple sidecar loop is adequate until then.
- No arbitrary DOM mutation, browser automation, `eval`, shell tool, repository-wide
  filesystem access, or implicit network capability for the agent.
- No editable SVG/PNG/HTML artifact; no manual visual correction outside a revision.
- No automatic Git commit, pull request, default-branch write, merge, or deployment.
- No attempt to relocate the upstream typed semantic model into kr0ki. This plan owns
  session/revision/provenance state around render inputs, not the UFO vocabulary.
- The production identity provider, multi-tenant retention policy, and semantic merge
  rules remain decisions to make in Phase 0/4; they must not be hidden behind a framework
  default.

## 9. Operational tracking

Track implementation as a parent b00t task with one child task per phase. Record the
accepted state schema, renderer recipe evolution, and any failed replay as b00t lessons.
Update this plan and `AGENTS.md` when a contract decision becomes implemented behavior;
do not let the sidecar's incidental implementation become undocumented architecture.
